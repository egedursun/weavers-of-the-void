# Legacy world migration and media storage

This plan moves the existing legacy world (the `~/aerona` Node app) into the rewrite, together with its media. It replaces decision 2 ("no import of the legacy DB").

## Feasibility by category

| Category | What it covers | Feasibility | How |
|---|---|---|---|
| Core lore | entities, names, descriptions, depth, stats, epithets, locations, bonds, chronicle and its links, epoch narratives, canon facts, lexicon, languages, threads, prophecies, legends | **Full** | Direct column and enum mapping. Names go through the name registry; any duplicate gets a Roman numeral and is reported. |
| Pantheon | creator, sons (stats, powers, stars, existence, reputation, passions, plans, epics), foreign gods, son relations, councils, prayers and messages | **Full** | Direct mapping. Power and passion keys map to the new enums. |
| Cosmos | stars, worlds (type, physics, climate, leak, mirror twin), routes, journeys | **Full** | Direct mapping. Maps are regenerated by the new cartography. Stored legacy map positions (`harita_xy`) are kept as position hints, so places stay where they were. |
| Media | every image, its caption, cover flag and target | **Full** | Originals are copied into the media store. Thumbnails are not copied; they are rebuilt on demand. |
| Rules | world rule overrides | **Full** | Mapped through `rules-registry.json` (`old_namespace`/`old_key`). Only 3 overrides exist. |
| Lore language | | **Full** | The migrated world is created with `lore_language = turkish` (decision 1 supports it). Lore text stays as written. |
| Structured state that legacy kept in tags or text | wars and their sides, armies, tributes, captives, debts, cult membership, syncretism, civilization tier, society shares and stocks, water regions, temple and underworld flags, legend categories | **Mostly** | One-time conversion. Tags (`taraf:`, `basamak:`, `senkretik:` and others), bonds (`taraf`, `harac_oder`, `esir`, `borclu`, `ateskes`) and the society JSON are parsed into the typed tables. Anything the converter cannot place with certainty is listed in the migration report. On the first epoch the engine recomputes derived state (faith, prosperity, capacity, relations drift) from the typed data. |
| Fate and agent bookkeeping | verdict history, motif tags, turn counters, pending turns | **Partial** | Verdicts become `accepted` or `rejected` from the legacy status. Motif tags are left empty; the tired-motif detector starts fresh. A paused legacy epoch is not resumed: migrate only from a finished epoch. |
| Undo ledger | 774 player actions | **Not migrated** | Legacy entries store before/after snapshots in a different shape, and undoing a pre-migration action against the new schema is unsafe. They are kept as a read-only history list instead. |
| Telemetry and logs | LLM metrics, server log | **Not migrated** | Operational data only. |
| Legacy backups | 15 earlier snapshots | **Not migrated** | Only the current world is migrated (user decision, 2026-11-01). |

Overall: every piece of lore, every image and every relation the player can see is carried over. What is not carried is operational history (undo entries, telemetry, logs) and any legacy state that the new engine derives again by itself.

## Design

### Media store (MinIO)

- New backend abstraction `MediaStore` with two implementations behind one interface: `S3MediaStore` (MinIO in Docker, any S3 in production) and `FileMediaStore` (local development without Docker, and tests).
- Objects: `originals/<image-id>.<ext>` and `thumbnails/<width>/<image-id>.webp`. Thumbnails are generated on first request and cached in the store.
- Image rows keep the object key, content type, size and checksum (SHA-256, also used to skip duplicates during migration).
- `docker-compose.yml` gains a `minio` service with a named volume, a healthcheck, an init step that creates the bucket, and credentials from `.env`. The backend talks to it over the internal network; the browser receives images through the backend (`/api/media/...`), so MinIO is never exposed.
- Backups: the SQLite backup stays as it is. Media are already durable in MinIO; the world package export streams the objects into the archive.

### Migrator

- A separate module `backend/src/aerona/migration/legacy/` and a command `make migrate-legacy LEGACY=~/aerona/data`.
- The legacy schema vocabulary (Turkish table, column, enum and tag names) is data, not code: `migration/legacy/schema_map.json`, generated from `docs/spec/01-data-model.md`. The migrator code uses only English names and reads the map. This keeps the "no Turkish in code" rule.
- Steps:
  1. Take a consistent read-only snapshot of the legacy database (SQLite backup API). The legacy app may keep running.
  2. Validate: the legacy schema version is known and the epoch is closed (no paused turns).
  3. Create a new world with `lore_language = turkish`, the legacy seed and the mapped rule overrides.
  4. Import in dependency order inside one transaction: stars and worlds, creator, sons, foreign gods, entities (with the name registry), bonds, chronicle and links, epochs and narratives, facts, lexicon, threads, messages and prayers, councils, relations, folk beliefs, routes and journeys, scores and achievements.
  5. Convert tag and text state into the typed tables (wars, sides, armies, tributes, captives, debts, reverences, tiers, societies, flags).
  6. Upload images to the media store and link them.
  7. Regenerate world maps, keeping legacy positions as hints.
  8. Run the integrity repairs and the full constraint check. Any failure rolls everything back.
  9. Write `migration-report.json` and a readable `migration-report.md`: counts per table, everything renamed, everything that could not be placed, and every tag that was not understood.
- Idempotent and repeatable: it always writes into a fresh database, so it can be re-run after the rewrite changes, and the legacy data is never modified.
- A dry-run mode prints the report without writing anything.
- Tests: a fixture built from a small slice of the real legacy schema, round-trip counts, tag conversion cases, image dedupe, and a full run on the snapshot in CI-like local runs.

### Order of work

1. Media store abstraction plus MinIO in compose (independent of the schema).
2. Migrator, after the current fix round has settled the schema (the agents are still changing tables).
3. A dry run on the real snapshot, the report reviewed together, then the real migration.
